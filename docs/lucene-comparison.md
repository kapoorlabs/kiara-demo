## Workload matrix

The default suite now follows the reference TypeScript report's **five dataset entries across three
distinct workload families**, rather than two scales of one mixed fixture. Each family has its own
data distribution and query set. Catalog and schedule sizes are independently executed, not extrapolated.
Schedule has no keyword workloads; `n/a` is intentional, not zero latency.

| Family | Data and scenario coverage |
| --- | --- |
| retail-3788 | The same real retail CSV as the TypeScript report: country-list any/all/exclusion, historical fractional price comparisons, sales volume, multi-word typo search, stemming, prefix predictions, correction and projection |
| catalog-10000 / catalog-100000 | Independent seeded products: skewed status, region IN, three-field AND, enum tiers, sale flags, missing suppliers, all integer comparisons, decimal correctness probes, long counters, varied string/numeric lists, projection, typed reconstruction, limits and multi-word keyword search with hard filters |
| schedule-10000 / schedule-100000 | Independent seeded events: calendar dates, exclusive/inclusive time windows, any/all date/time lists, numeric and prefixed ranges, interval lists and correlation, nullable seasons, date/time range lists, four-field intersections and typed/limited results |

Synthetic Java records use a different PRNG/schema encoding from TypeScript; only retail source bytes
are identical. These results compare **Kiara Java against Lucene**, not Java against TypeScript timings.
All families use the shared annotation-bearing Java record to avoid separate engine implementations:
irrelevant fields are null, not filled with mixed-fixture dummy data. This still incurs shared-schema
overhead and is not a minimal domain-specific schema benchmark.

## Feature coverage and Lucene mapping

Every timed scenario is checked against a deterministic, engine-independent scan oracle before warmup.
All eleven Kiara `Operator` values are exercised. "Equivalent" refers to the tested result sets, not identical APIs.
No Lucene query falls back to scanning the original records.

**Build failures are first-class results, not zero-latency wins.** The realistic schedule generator
exposed Kiara 2.0.15's interval-index build failure (fixed in 2.0.16):
`IndexingException: Static data indexing failure`, with an underlying
`IllegalArgumentException: Comparison method violates its general contract!` from
`ComparableTimSort` through `SearchableRange.prepareForSearch`.
Any such failure is recorded as `BUILD_FAILED` with stderr evidence in the raw results. Every blocked query
is still listed, but Kiara match counts, latency and retained-heap estimates are `n/a`.
Lucene is measured independently. The summary shows successful build counts; no schedule latency
ratio is fabricated when Kiara cannot prepare the same records. The published library is used
without local patches, and the generator is not rerolled to conceal failures.
The 10,000-row schedule is also covered by a correctness regression test.

**Correctness finding: fractional numeric comparisons are not equivalent.** Kiara converts
numeric index keys and query values using `Double.parseDouble(value).longValue()` in NumericUtil.
For example, prices 19.00, 19.50 and 19.99 all match `<= 19.50`, and values below 950.25 in the
950 bucket can match `>= 950.25`. Lucene uses DoublePoint ordering / exact decimal terms and matches
the independent oracle. Decimal scenarios in retail and catalog are retained to expose the difference, but
**excluded from all aggregate speed ratios**. A dedicated regression test verifies this behavior.
Only this explicitly recognized truncation behavior is allowed to continue for structured queries;
an unexpected structured mismatch still aborts the run. The raw results include the oracle count,
missing/extra counts and example IDs.
In retail, truncation can cause **missing** results too: `price < 0.20` becomes an integer-bucket
comparison against zero. Combined fractional-price filters are checked with the same explicit model.

**Retail stemming has different cross-field semantics.** The Java fixture indexes raw title tokens
in `name` and stemmed tokens in `keywords`. For `lanterns`, Kiara's best-match column selection returns
the 18 singular-token records, while Lucene's cross-field union returns all 20 singular/plural records.
The independent oracle expects both forms. This recognized 18-record selection is explicitly checked
and marked `TEXT_RESULT_DIFFERENCE`; retail stemming is excluded from speed aggregates.
The general adapter is not silently narrowed to hide this difference.

**Text quality is measured, not assumed.** Multi-word keyword retrieval on varied catalog titles can
differ from the all-intended-tokens oracle. Such cases are marked `TEXT_RESULT_DIFFERENCE`, with
missing/extra records retained in the raw results and returned-record precision displayed below.
Hard filters and valid record IDs must still hold or the run fails. Only scenarios that pass full
result-set equivalence in **every fork of both engines** contribute to the equivalent keyword ratio.
A `n/a` speed ratio does not hide the timing: both engines' p50/p95 are still reported.

### Features outside the head-to-head measurements

Lucene also provides BM25 relevance scoring, phrase/proximity queries, arbitrary nested Boolean queries,
analyzers and language pipelines, updates/deletes, durable indexes, segment merges, and concurrent search.
This benchmark does **not** disable those capabilities to claim Kiara-only feature support:
it uses constant-score queries because Kiara's structured result sets do not have equivalent BM25 rankings.
Lucene has native range/point indexing; it is not treated as a string-only fuzzy search library.

This Java Kiara API is a prepared, in-memory read-oriented store with an AND list of Conditions,
annotation-driven typing and built-in cross-field keyword discovery. Keyword best-match chooses a
matching subset, not a relevance-scored union. Its suggestion API selects one correction rather than
enumerating every edit-distance candidate. No TypeScript-only unit conversion or query-language
parsing feature is attributed to the Java artifact.

## Dataset and methodology

- Catalog seed 20261027; schedule seed 20261028. See
  [record schema](../benchmarks/src/main/java/com/kapoorlabs/benchmark/BenchmarkRecord.java) and
  [dataset-specific generators and queries](../benchmarks/src/main/java/com/kapoorlabs/benchmark/Datasets.java).
  [Retail source, license, checksum and column mappings](../benchmarks/src/main/resources/README-retail.md).
  Catalog uses 20 categories, 50 brands, 15 tags, 9 numeric sizes and a varied title vocabulary.
  Schedule uses 365 days, 36 list-date slots and 12 booking days. Calendar values are in 2026.
  The raw results include a SHA-256 of serialized input POJOs per fork; all engines/forks must agree
  for each dataset. These are **not movie-CSV measurements**.
- One fresh JVM per engine/dataset/fork, sequential execution, alternating engine order across forks.
  The same randomized scenario order is used for both engines in each fork. No concurrent benchmark workers.
- Both engines get identical in-memory POJOs. Fixture creation, correctness scanning, JVM startup and
  report writing are outside measured time. A 64-row engine build/query primes classes before timing.
- Successful build time includes loading, index preparation and making search available. Failed
  attempts record only elapsed attempt time and explicit failure, not a successful build or heap estimate.
  Lucene writer is committed
  and closed before opening DirectoryReader. It uses ByteBuffersDirectory (no disk I/O), not a filesystem
  index. Kiara prepareForSearch is included. This is a warmed build measurement, not cold startup.
- Additional retained heap = post-build Java heap after three requested full GCs minus pre-build heap
  after three requested full GCs. Input POJOs remain live in both measurements. This is an estimate,
  **not allocation volume, peak memory, RSS, or a full accounting of native memory**.
- Lucene query-result caching is disabled. Normal engine internals, dictionaries, compiled JIT code and
  index buffers remain warm. Query construction, result materialization and ID extraction are timed;
  correctness comparisons, sorting for validation and JSON output are not. Lucene's optional
  JDK vector module is enabled in both workers.
- Each scenario warms for at least the configured duration and at least three queries, then records
  queries until the configured time budget or sample cap, with at least min(5, cap) samples.
  This bounded sampling follows the TypeScript harness pattern; slow queries may have fewer samples
  than fast ones. Tables expose each engine's per-fork sample-count range. p50 and p95 use nearest-rank percentiles.
  Tables show median per-fork p50 and median per-fork p95, **not a pooled percentile or confidence interval**.
  Raw nanosecond samples preserve GC/JIT/outlier effects. This is a standalone harness, not JMH.
- Most structured scenarios project only ID. Projection retrieves three columns. Full-object and keyword
  cases reconstruct typed POJOs (Kiara reflection; Lucene stored JSON/Jackson). The latter includes adapter
  costs, so it is not a pure index-traversal comparison. Lucene stores JSON plus projection fields;
  Kiara uses its native reconstructable store. Lucene's schema also carries exact terms for typed values
  and a combined discovery field. These storage choices affect build time and retained heap.
- Kiara may normalize reconstructed case-insensitive, stemmed, and list values. Validation checks matched
  IDs, exact projection keys/values, typed scalar values and collection membership; tests also check normalization
  behavior. IgnoreIndex fields are retained in reconstructed records but not searchable.
- No-match and inclusive/exclusive boundaries have separate tests. Every benchmark invocation is
  consumed through a volatile sink; all timed scenario results are checked before warmup.
- Text scenarios return all matches, not a relevance-ranked top 10. The oracle requires every
  intended title token; returned-record precision is the fraction satisfying that predicate.
  Hard filters must hold for every result. These are retrieval/quality checks, not BM25 scores.
  Prefix results are validated as completed dictionary words; suggestions are checked against an
  independent edit-distance oracle, with Kiara returning one candidate and Lucene up to ten.
  The Lucene keyword adapter covers the listed fixture queries; it is **not a general reimplementation
  of Kiara's keyword discovery/subset algorithm**. Best-subset, suggestion multiplicity, and limited
  subsets are explicitly excluded from aggregate speed ratios. Prefix terms are also excluded from
  document-query aggregates.
- Repeated fixed queries and a shared Windows host favor hot-cache behavior.
  No concurrency, cold-cache, changing-query distribution, persistent-index, relevance-quality,
  ingestion-update, or production-tail-latency claim follows from these numbers.

## Reproduce

Requires JDK 21+ and the repository's existing Maven wrapper. From the repository root in PowerShell:

```powershell
.\mvnw.cmd -f benchmarks\pom.xml clean verify
& "$env:JAVA_HOME\bin\java.exe" -jar benchmarks\target\kiara-lucene-benchmark-1.0-SNAPSHOT.jar
```

Default: retail-3788, catalog-10000, catalog-100000, schedule-10000 and schedule-100000;
three JVM forks per engine/dataset (30 worker JVMs). Each scenario has a 1,000 ms measurement budget,
at least five and at most 61 samples, and at least three / 50 ms warmup queries.
Worker heap is fixed at 256 MiB initial / 4 GiB maximum using G1.
A smaller smoke run can be written separately without replacing this report:

```powershell
& "$env:JAVA_HOME\bin\java.exe" -jar benchmarks\target\kiara-lucene-benchmark-1.0-SNAPSHOT.jar `
  --datasets retail-3788,catalog-1000,schedule-1000 --forks 1 --samples 5 --warmup-ms 10 --budget-ms 100 `
  --output benchmarks\target\smoke.json --report benchmarks\target\smoke.md
```

`--datasets` selects any subset of the default entries or other synthetic sizes of at least 1,000.
`--sizes` remains a legacy alias selecting the original optional mixed fixture and cannot be
combined with `--datasets`. `--samples`, `--budget-ms`, `--warmup-ms` and `--forks` control measurement.
All chosen settings are recorded in the raw results and this report.

Dependency overrides via Maven are supported for experiments; version metadata is filtered from the POM
into the executable. The raw results include the executable's SHA-256. Do not mix outputs from different builds.
Version provenance: [Kiara artifact](https://repo.maven.apache.org/maven2/com/kapoorlabs/kiara/2.0.16/),
[Lucene artifact](https://repo.maven.apache.org/maven2/org/apache/lucene/lucene-core/10.5.2/),
[Lucene query APIs](https://lucene.apache.org/core/10_5_2/core/org/apache/lucene/search/package-summary.html).

## Interpretation

Use the per-scenario numbers and match counts to identify workloads relevant to your application.
Large result sets include substantial object-allocation and materialization work. A geometric mean
weights each selected scenario equally; it does not represent a production request mix.
Build time and retained heap are separate tradeoffs, not part of the query speed ratio.
Rerun on the target hardware with representative data and query diversity before choosing an engine.
